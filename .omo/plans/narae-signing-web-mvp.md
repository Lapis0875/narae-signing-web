# narae-signing-web-mvp - Work Plan

## TL;DR (For humans)

**What you'll get:** A self-hosted Korean event-signature board: one administrator can prepare an event board, invite assigned tablet signers through a private link, monitor completed signatures, and download a closed board as a PNG.

**Why this approach:** The product stays a small same-origin system with one backend process and private storage, while the risky boundaries (identity, signature data, board state, and deployment) are made testable before the live event flow is assembled.

**What it will NOT do:** It will not provide legal e-signatures, public views, smartphone signing, email account flows, multi-admin workflows, automatic offsite backup, or a login-failure alert service.

**Effort:** XL
**Risk:** High - encryption, state races, tablet behavior, and first production deployment must all work together.
**Decisions to sanity-check:** `production` is a movable deployment alias pointing at immutable release images; public mutations use CSRF; physical iPad/Android validation remains a release gate because it cannot be honestly replaced by browser emulation.

Your next move: start the worker plan or request a high-accuracy review. Full execution detail follows below.

## Scope
### Must have

- Build the approved Vite/React/TypeScript frontend, Spring Boot modular monolith, PostgreSQL, private MinIO, Docker Compose/Portainer, NPM proxy, and GitHub Actions delivery path.
- Deliver owner-scoped board authoring, strict roster/import rules, normalized slot layout, private share links/QR, tablet identity and vector signing, manager-only live updates, closed-board PNG, and permanent deletion.
- Enforce encrypted roster/signature/background storage, secure cookie sessions, CSRF, exact identity matching, accepted device support, bounded input/rate behavior, and no sensitive logging.
- Prove the result with backend, frontend, browser, deployment, concurrency, and release-gate evidence.

### Must NOT have (guardrails, anti-slop, scope boundaries)

- Do not add public signup, SMTP/email reset, multi-admin ownership, public full view, anonymous slots, smartphone support, multilingual UI, legal-signature claims, audit trails, non-PNG export, external backup/recovery, or login-failure alerts.
- Do not add Redis, a queue, microservices, a worker service, a public MinIO endpoint, browser token storage, a frontend/backend shared-types package, or live signature-stroke broadcasting.
- Do not replace exact raw-value roster identity matching, server-authoritative state checks, application-layer encryption, or the specified same-origin deployment topology with a looser substitute.

## Verification strategy
> All automated verification is agent-executed. The physical-tablet checklist is a separately owned external manual release gate.
- Test decision: TDD for cryptography, state transitions, concurrency, import parsing, authorization, and rendering; tests-after for visual interaction, Compose, and deployment wiring. Use JUnit 5 + Testcontainers, Vitest, and Playwright Chromium/WebKit.
- Evidence: before any branch starts, the coordinator resolves `NARAE_EVIDENCE_DIR` to the absolute `.omo/evidence` directory under the retained primary `main` worktree, then records that absolute path and a unique attempt ID in `baseline-narae-signing-web-mvp.env`. In this plan, `<attemptDir>` means exactly `$NARAE_EVIDENCE_DIR/attempts/<attempt-id>`: it is never relative and never inside a feature or disposable worktree. A branch agent may create only its own task evidence file there; the coordinator must verify its checksum and final path before any associated worktree is removed. All ledger/provenance TSV writes are coordinator-only and use the locked, atomic protocol below.
- A deployment owner operates the physical iPad Safari and Android Chrome check after the automated release checkpoint. It is never replaced by Playwright emulation. If no enrolled device/control bridge is available, record it as blocked and do not claim production readiness.
- All fixtures use synthetic roster data and generated share tokens. Evidence must redact cookies, master-key material, real IPs, credentials, and any real participant information.

- A single owner can create a board, import at most 50 exact identities, place every person without overlap, open it only when valid, share a private QR/link, and close/reopen/delete it under the approved lifecycle.
- An assigned tablet signer can identify using exact raw fields, draw/clear/retry a vector signature once, and cannot submit after stale link/revision/close/delete changes; no other participant data is disclosed.
